# Inkling SQ-10 发现流水线与上下文实测

结论：服务甜点是 **16,384-token 窗口 + 2 个推理槽位**，但业务请求甜点仍是 **每批 8 条搜索结果、约 2.3–3.1K 输入 tokens**。窗口本身不是瓶颈；实际输入长度和输出长度才是。Inkling 2 Mini SQ-10 权重包声明 `model_max_length = 1,048,576`，Strata 启动窗口可调。本次在本机实测到 32,768；更大的上下文不等于可以塞进现有 45 秒客户端超时。

## 冷启动与输入延迟

短输入第一次请求会有 KV/调度预热，冷启动后常见固定开销约 2 秒。用历史搜索片段构造 1K–13K 输入，每个长度两次，淘汰明显冷启动样本后拟合：

**首 token 延迟 ≈ 2.1 秒 + 输入 tokens / 488 tokens/s**

| 实际输入 tokens | 首 token 秒（均值） | 总耗时秒（均值） | 样本 |
|---:|---:|---:|---:|
|1,048|5.0|5.6|2|
|2,048|4.8|5.5|2|
|3,048|9.5|10.2|2|
|4,048|11.5|12.0|2|
|5,047|10.2|10.9|1|
|5,048|14.3|14.8|1|
|6,048|15.1|15.8|2|
|7,048|14.9|15.5|2|
|8,048|16.7|17.4|2|
|9,048|22.1|22.8|2|
|10,048|21.0|21.6|2|
|11,048|26.6|27.3|2|
|12,048|27.7|28.3|2|
|13,048|28.1|28.8|1|

到 13K 为止没有“预填充突然变慢”的架构拐点；主要变陡来自总时延公式：约 29 tokens/s 的生成速度下，输入每增加 1K tokens 加约 2 秒，输出每增加 500 tokens 加约 17 秒。15.6K 输入的短答案实测首 token 37–38 秒，30K 输入为 74–77 秒，都超过或接近现有客户端 45 秒超时。

## 窗口、输出与 45 秒超时

16K 窗口的安全上限不是 16K 输入。若仍按当前批量抽取可能输出 500 tokens，输入控制在约 **12K tokens** 以内更合理；15K+ 输入只有在把客户端超时提高到 90 秒以上、且预留输出空间时才值得用。默认 16K 是甜点，因为它覆盖现有 3K 输入的四倍证据余量，同时 KV 成本可控；32K 只是可运行上限，不是吞吐甜点。

## 并发槽位与空闲延迟

上次串行与并发测试选取了不同的搜索批次，撤回 44% 吞吐增益。复测固定两条请求（输入 2964、2291 tokens，输出 310、269 tokens），两槽服务按串行、并发、并发、串行回放。两次均命中前缀缓存时，并发 15.32 秒，串行 20.28 秒，两批全部结束的用时减少 24.5%。两次零缓存观测分别为串行 78.66 秒、并发 28.71 秒，但首次串行中有一条耗时 63.72 秒。

这条慢请求不是模型生成慢。服务器日志显示它在读入第 2964 个 token 后停顿，等待约 42 秒才重新分块读取；解码仍达 27.1 tokens/s。用同一条 2966-token 请求测引擎自带的 GPU keep-alive（每次命令缓冲后活跃 120 秒）：活动后等待 5 秒再次运行，首 token 为 6.7 和 6.2 秒；等待 135 秒后，首 token 为 49.9 秒。服务配方已把 launchd 环境设为 `STRATA_METAL_KEEPALIVE_MS=0`，空闲后按初始化成本进入，而不是让工作集保持活跃两分钟再进入低吞吐状态。

并发判断：每条输入约 3K tokens 的发现任务，2 槽在缓存命中时可减少两批总耗时约四分之一；因此仍是批量吞吐甜点。交互式短问答继续使用当前服务，单槽只在资源最紧张时考虑。## 长上下文正确性

在 2K、4K、8K、12K 的真实历史搜索片段中，把一条明确标注的证据放在开头、中间、结尾：12/12 都抽到了正确的公司名和国家，没有随位置或长度退化的语义拐点。主要问题是格式不稳定：有时按提示返回 JSON 对象，有时包一层数组。7/12 是严格对象；5/12 是同内容数组。对这 5 条失败请求启用 Strata 原生 `response_format.type=json_schema` 后，5/5 返回严格对象且字段正确。每条输入增加 133 tokens，耗时 5.52–27.17 秒。对象调用方可以按字段契约启用该参数。

## 发现流水线实际表现

- P3 七例在最终 16K 服务端均返回有效 JSON，标签 7/7 正确。冷启动后首题 8.47 秒，其余六题 1.18–1.44 秒。
- 历史归档 10 组搜索结果、每组 8 条，保留原 Go 批量抽取提示。2048 窗口全部拒收，实际输入 2291–3101 tokens。5120 窗口的十批回放全部成功，端到端中位 19.94 秒，最长 33.27 秒。129 条标为真公司的名称都出现在对应行的原文里（忽略大小写和空白）。其中包括媒体“36氪”和截断的英文别名，仍需媒体过滤和别名去重。
- 受控样例中，单条抽取过滤掉政府新闻噪声，保留两家企业。名称规范化两例正确。官网识别一条返回根域，一条在只有招聘页时返回空。公司画像保留业务邮箱并排除个人邮箱，识别出口德国。
- AI 可见度推荐输出可解析，但将科沃斯与 Ecovacs 分列。Python 推荐变体也完成了一次真实采购查询，生成结果需查证。种子拓展 Go 模板把业务查询插在“家中国公司”之前，输出回显模板并生成“石头科技家中国公司”，不宜直接入库。
- 回放 Python 证据判断的 ICP、资质、联系归属、企业画像、评分五段提示，含 JSON 模式。五段都输出有效 JSON。样例支持出口德国，但模型也断言官网是主要成交渠道，为空联系人列表生成索引，给缺少依据的岗位打分。建议仅将这些输出作为候选事实，入库前核实原句、联系人索引和评分条件。

## 内存

原生 Metal 生成进程 + Qwen3-Embedding 进程的 20ms 采样 peak footprint：5K 窗口 1.63 GB，16K 窗口 1.997 GB，32K 窗口 2.535 GB。这是测试期间的 macOS 物理 footprint，不包含 Python HTTP 层和 Docker relay，也远不是 Metal API 的虚拟分配总量。16K/2 槽运行一次双请求峰值到 2.877 GB。统一内存上的 Metal 预留应按容量风险另行限制，而不是把分配值直接当作物理占用。

本次是对本地 HTTP 端点的只读回放；没有修改 leadops/mvp 生产代码。
## DSpark 在六条发现流水线请求上的端到端耗时

同一 Metal 构建、SQ-10、FP8 KV、16K 窗口、两槽，四轮顺序为关闭、开启、开启、关闭。每轮预热后串行回放同一组请求。表中为每种配置两轮的算术平均，计时从 HTTP 请求发出至完整响应。公司抽取与官网识别 temperature=0.1，名称规范化为 0。

| 请求 | 关闭（秒） | DSpark（秒） | DSpark 接受 / 提议（每轮） |
|---|---:|---:|---:|
| 单条公司抽取 | 2.83 | 1.91 | 38/49 |
| 批量公司抽取 | 3.66 | 2.30 | 52/63 |
| 官网正例 | 3.60 | 4.03 | 43/147 |
| 官网负例 | 2.41 | 2.17 | 25/56 |
| 公司名称规范化 | 5.88 | 5.45 | 16/21 |
| 媒体名称规范化 | 5.39 | 4.78 | 19/19 |

每组 12/12 返回有效 JSON 并通过业务判定。公司抽取核对完整列表与字段，官网只核对 URL，名称规范化核对完整对象。官网正例的理由改变，输出从 62 增至 65 tokens。两条规范化请求单是预填充就各用约 4 秒，即使草稿全中，端到端收益也有限。

六条总耗时，关闭为 22.23、25.29 秒，开启为 20.70、20.58 秒，按两轮均值缩短 13.1%。样本来自六条固定请求，每条权重相同。优先在公司抽取验证 DSpark，生产全局默认保留关闭。本轮记录完整响应耗时，未采集流式首 token 延迟和内存峰值。原始记录在实验目录 `dspark-business/results.jsonl`。

## DSpark 按实测耗时暂停投机

使用同一引擎，在六条固定发现请求上比较持续投机和 `STRATA_INK_SPEC=adapt`。自适应模式先估计普通解码成本，再根据每轮验证实际提交的 token 数和耗时决定是否暂时回到普通解码。四轮依次为持续、自适应、自适应、持续，每轮均先预热。

官网正例四次都输出同一段 65-token JSON。开启自适应后，每轮草稿提议数从 147 减到 84，完整耗时从平均 3.37 秒降到 2.94 秒。跑完六条请求的平均耗时从 16.93 秒降到 16.50 秒。两组各 12/12 通过原有业务判定，官网只评分 URL。该测试测量单请求串行回放。

## 两路并发时的 DSpark 调度

两个 HTTP 客户端取同一组六条请求，任一客户端完成即取下一条。服务配方下，全部完成的平均用时为关闭投机 19.46 秒、自适应 DSpark 18.62 秒，各 12/12 通过业务判定。并发请求的 HTTP 草稿计数均为零。另一次带原生日志的实验中，两个槽都提出并接受了候选，HTTP 回报仍为零。原生 BDONE 行含有计数，HTTP 层遇到 Inkling 结束 token 时提前关闭了生成器。批处理清理路径使用该模型的结束 ID 后，六条双槽合成请求均返回正确 JSON，并报告了共 155 个草稿提议和 127 个接受。九项批处理回归测试通过。修复已提交 [Strata PR 7246](https://github.com/Niko1221/Strata/pull/7246)，本地服务分支提交为 `65ac7436`。修复后用服务配方重放同样的六条双槽业务请求，两轮自适应共提出 52 个候选，接受 40 个。关闭和开启两组各 12/12 通过，每轮六条全部完成的平均耗时分别是 18.84 秒和 18.64 秒。

实验调度在两个槽都读完提示后，轮流让每个槽执行一个投机验证轮次。在早期构建上，六条混合请求耗时从 19.02 秒降至 17.25 秒。在基于上游 `c23477403` 调度代码的候选版本上，基线两轮为 18.73、18.90 秒，轮流投机为 19.87、19.72 秒，各 12/12 通过。前两条公司抽取同时完成的平均时间从 5.42 秒降至 3.45 秒。

独立合成测试要求按原顺序输出四个公司全称。第一组输入将句点紧接在公司名后，两种配置各 0/12 严格匹配。将列边界写成显式分隔符后，两种配置各 12/12 严格匹配。此时基线两轮为 5.70、5.83 秒，轮流投机为 15.36、5.92 秒。服务采用原有双槽调度，轮流投机原型留作研究。
