# Inkling SQ-10 的循环投机与流式服务

## 三种并行机会

| [LoopCache 论文](https://arxiv.org/abs/2611.24301) · [实现](https://github.com/zZzZ9zZ9/LoopCache/tree/b61003fcae086f15be302a7f35a2fb95b39d3023) | 多个在途位置按循环深度轮转读取长前缀 KV。中间预测可以替换草稿，并丢弃依赖旧 token 的后继。 | 适合研究长前缀解码。移植需要同时维护各遍 FP8 KV、短卷积历史和分歧回滚。应在真正的长输入上测。 |

## DSpark 的 thinking 预算与续写

单槽 `BGEN` 的 `hold` 指令用于暂停生成，以便服务继续管理 reasoning 预算。此前线性与树形投机路径都可能越过边界。使用维护者复核的确定性后端测试，原 PR 通过 20/28，修正请求类型判断后通过 28/28。M6 上用真实 SQ-10 和 FP8 KV 复测，线性和树形两种模式均恰好生成 2 个 token，返回 `hold`。同槽续写复用了 727 个前缀 token，后续 20 个 token 均与新槽逐个一致。上游提交 `d1b0410c`，本地实验查表补丁同步提交 `c00344c1`。[Strata PR #7225](https://github.com/Niko1221/Strata/pull/7225)

标准 FP8 服务构建已纳入这项修复，本地提交 `0787df11`。隔离实测中，`block`、`tree` 和 `adapt` 均在第 2 个 token 暂停，三种模式的同槽续写都复用 727 个前缀 token，随后 20 个 token 与新槽一致。`adapt` 的这次暂停发生在普通解码步骤。双槽关闭草稿的 P3 回归为 7/7，热请求完整响应中位数 1.33 秒。测量记录在 `hold-service.nlGGHb`。

## Apple M6 的选择

单活贪心打标选 MXFP8 DFlash2，目标和草稿前缀缓存使用 FP8 E4M3。此前七题两轮与普通解码逐 token 一致，原生请求完成中位数 0.895 秒，同轮 DSpark 为 0.997 秒。另一组浅循环试验中，双位置交错验证为 1.832 秒，同轮 DSpark 为 0.990 秒，双方均为 14/14。浅循环试验中起草及追赶前缀中位数 27.81 毫秒，验证 58.09 毫秒，两阶段依次执行。跨物理层合并专家工作只节省了双位置完整前向平均约 0.39 毫秒。

## 真正从 HTTP 读到正确结果需要多久

隔离 Strata 服务使用 16,384 上下文、单槽、chunk 512、temperature 0。客户端以首个非空内容 delta 计 TTFT，以 `[DONE]` 计完整时间。第一轮七次请求的 JSON 和标签均正确，目标接受 166/224 个候选。第一题输入 105 tokens，首字 7.420 秒，完整 8.383 秒。其余六题输入 87–111 tokens，首字中位 0.436 秒，完整中位 1.012 秒，引擎报告的生成速度中位 48.45 tokens/s。

复跑七题后立即重复第七题，缓存命中 100 个输入 token，重算 1 个。重复题首字 0.044 秒，完整 1.059 秒，草稿提议数为零。相邻的首次请求为 0.435 和 1.068 秒，提出 35 个候选，接受 27 个。复用在这对请求上主要缩短首字时间。此次 HTTP 轮次没有重新采样物理峰值，之前同配置原生对照的目标、草稿与嵌入合计峰值为 3,166,328,280 字节。

实验服务入口已提交至本地 `feat/inkling-metal-service` 的 `8409bfe4` 和 [Strata 草稿 PR #7247](https://github.com/Niko1221/Strata/pull/7247)。目标构建还使用了 [Metal FP8 PR #6983](https://github.com/Niko1221/Strata/pull/6983)。测量使用隔离实验端口 8397。原始逐请求数据在实验根目录的 `dflash-http/results.jsonl` 和 `dflash-http/repeat.jsonl`。

## 修复提示词检查点恢复后的草稿位置

旧实现恢复目标模型的提示词时，草稿器仍保留上次生成末尾的位置。修复后使用目标保留的特征重建草稿缓存。七道短题各立即重复一次，每个版本都返回了 14 个正确且文本相同的 JSON。只统计七个缓存命中请求，修复前后完整中位数从 1.084 秒降到 0.819 秒，首个可见 token 从 0.049 秒增至 0.069 秒。草稿计数从提出 42、接受 25 变为提出 224、接受 166。本轮先运行修复版再运行旧版，每题每版本有一次缓存命中测量。

将同一机场题扩展至 2,801 个输入 token，重复请求命中 2,800 个。初始构建在恢复时发生 SIGBUS。加入 [FP8 缓存检查点宽度修复 #7215](https://github.com/Niko1221/Strata/pull/7215) 后，首次和恢复两次请求均完成。首次 DFlash2 提出 35 个候选、接受 27 个，类别为预期的 `airport`。重复请求的特征窗口不完整，草稿计数为零，类别为 `other`。同一二进制关闭草稿后，首次和恢复的普通贪心均输出 `other`。该例定位出长输入新请求上两种解码路径的结果差异。原始记录在 `dflash-http/restore`。本地提交 `08374cb7`，上游提交 `b75580b5`。

## 滑动窗口环宽度改变了长输入验证结果

2,801-token 机场题的首次分歧位于输出的第七个 token。普通贪心输出 `other`（995），原七候选验证输出 `air`（1619），续写为 `airport`。将每步候选数降至 1，目标验证器在该位置也选中 995。单候选试验在记录分歧位置后手动中止，只用于判断该位置的输出。

在 1,024-token 注意力窗口和 512-token 预填充分块下，将物理 KV 环从 1,024 行扩至 1,536 行，读写索引改用实际环宽度。窗口覆盖的证据范围保持 1,024。这个改动给批内较晚位置留出写入空间，较早位置仍能读取自己的完整历史。Metal 报告的目标 KV 分配从 336 MiB 增至 376 MiB。方案参照 [Strata PR #7098](https://github.com/Niko1221/Strata/pull/7098)。

隔离 HTTP 服务重新跑完整请求，七候选和零候选各跑一次首次请求和一次前缀命中。四次完整回答文本一致，全部为 `other`，均与机场题的预期标签不符。七候选首次验证接受 25/35 个 token，重复请求接受 1/7 个。这个输入支持修正环上的读写冲突，以保持目标输出一致。去掉逐块日志后，普通解码首次和恢复请求分别为 13.77 与 1.78 秒。七候选首次为 18.25 秒，恢复为 46.59 秒。恢复请求只提出一次七 token 块，接受一个；当前协议每次最多传输 2,047 行。完整响应很慢，但这些计时不能拆分出特征传输、MLX 预填充和 GPU 排队分别占多少。四条原始记录在 `dflash-width/quiet-{0,7}.jsonl`。

宽度 3 的验证使用加宽环，宽度 8 的分歧记录使用窄环，二者有两个变量同时变化。即使只验证三个位置，满环也可能提前覆盖旧键。已有记录没有分歧位置的 logits 间距。该机场样本可以检查填充鲁棒性和逐 token 一致性。真正需要从长上下文找证据的任务见《Inkling-FP8长上下文证据位置》。

### 满环的行索引复核

按 Metal 的批量写入和因果注意力寻址公式，将每个 KV 行的值替换为其绝对位置。在位置 2,801、可见窗口 1,024 的条件下，1,024 行物理环在 M=1、3、8 时分别有 0、3、28 次读取命中了被覆盖的行。M=8 的第一个查询独自读错 7 行。将物理环加宽至 1,536 行后，三个宽度的行索引都正确。这个索引模拟解释了为何验证器需要保留较早查询的历史。同一 Metal 二进制完成了六次独立前向。每次读取相同的 2,801-token 输入，输出上限统一为 12。窄环下 M=1、3、8 的第七个 token 分别是 `other`、`air`、`air`，后者续写为 `airport`。宽环下三个宽度的前 12 个 token 全部与普通贪心相同。固定验证宽度后，改变物理环宽足以改变本例的分类字段。物理环在预填充和生成阶段均生效，两阶段各自的贡献仍待分离。机场题的参考标签是 `airport`，宽环恢复了解码一致性，三种宽度都给出了错误类别。六次只用于定位分歧，单次耗时波动很大。逐 token 证据位于 `kv-factorial/limited-*.json`。

## 宽环与 DFlash2 的组合构建

服务构建将物理 KV 环设为 1,536 行，保留 1,024-token 的局部注意力范围。从 0.1.67 源码依次应用服务、宽环和 DFlash2 补丁后，单槽、16K、FP8 E4M3 配置通过全部七道 P3。首题完整 8.79 秒，后续六题首字中位 0.42 秒、完整中位 1.00 秒、生成速度中位 46.65 tokens/s。2,801-token 机场题首次及命中前缀后均返回完整 JSON，类别均误判为 `other`。

12,214-token 的中段证据题正确返回企业和目的地，完整耗时 33.40 秒，其中预填充 31.31 秒。单独运行 1,566-token 企业抽取时，从启动前至生成结束以 20 ms 为目标间隔采样目标、草稿和嵌入进程的合计物理占用，复测峰值为 2,956,023,280 字节。原生协议的首个 token 在 `T` 行，后续在 `BT` 行。修正采集器后取得完整 JSON。两次启动测量的较大峰值为 2,983,548,352 字节。原始记录在 `ring-service.GGjeE6`。

## 长输入的预填充分块

在上述宽环服务构建上，将同一条 12,214-token 中段证据请求按 1,024、512、512、1,024 的分块顺序运行，每次启动独立服务。FP8 KV、16K 上下文和单槽 DFlash2 相同。四次都返回正确的企业名称与目的地，JSON 对象符合请求的 schema。

| 预填充分块 | 两次完整响应（秒） | 两次预填充（秒） |
|---|---|---|
| 512 | 32.69、36.40 | 29.86、31.62 |
| 1,024 | 30.02、29.93 | 27.71、27.82 |

1,024 分块配套使用 2,048 行物理环。在单独的 12,081-token 原生协议请求上，启动至生成结束的三进程采样峰值为 3,442,333,432 字节。该请求仅靠提示词指定格式，返回数组包住的对象，字段正确、顶层类型错误。业务调用应使用本组 HTTP 测试的 JSON schema。两种分块的计时各来自同一题的两次请求。

同一背景的首尾位置补测中，四个请求均一次返回正确 JSON。证据在开头时，512 和 1,024 分块的完整时间分别为 31.76 秒和 65.86 秒，预填充分别为 29.37 秒和 28.98 秒。1,024 分块的 25-token 解码用时 36.73 秒。证据在末尾时，完整时间分别为 30.28 秒和 29.25 秒。结合中段结果，1,024 分块在这三个位置都缩短了预填充，整次请求仍受解码慢尾影响。首尾各配置只运行一次。默认服务采用 512 分块。原始记录见 `position-chunks/results.jsonl`。

另一个实验将 2,047 行草稿特征按连续内存段发送。75,460,608 字节的跨环负载逐字节匹配，套接字传输中位数从 34.37 ms 降至 33.43 ms。十个 HTTP 请求的答案和草稿接受数均与原实现一致。2,801-token 首次请求完整时间从 6.17 秒变为 6.24 秒。这项改动只保留在实验目录 `tap-spans.iIfgOl`。同目录的 `chunk-results.jsonl`、`mem-long.jsonl` 保存分块和内存结果。

## 真实负载上的无损性与净收益（定量）

对四个真实参展名录抽取批次（每个生成 293–305 tokens），在同一时段用当前上游构建跑逐 token 普通贪心作为参考，再与已有的 DFlash2 MXFP8 和内置 DSpark 输出逐 token 对比。三种路径在全部 1,196 个生成 token 上完全一致，无一个分歧位。机器内存空闲 68%。

| 解码路径 | 四批次 decode 耗时（秒） | 相对普通 |
|---|---|---:|
| 普通逐 token 贪心 | 9.57 / 9.15 / 10.59 / 10.96 | 1.00× |
| 内置 DSpark（早前测量） | 7.6 / 6.6 / 7.3 / 7.5 | 约 1.4× |
| DFlash2 MXFP8（早前测量） | 5.9 / 5.3 / 5.3 / 5.5 | **约 1.8×** |

早前与本次 decode 计时口径一致（首 token 到最后 token），但跨时段测量受机器状态影响，比值按同表内读取。四份输入上观察到的解码收益和一致性足以支持继续试用，生产请求的分歧频率仍未知。

## 验证宽度扫描：4–7 进入甜点区，慢尾是下一个瓶颈

用 kv-factorial 宽环构建（ring 1536、单槽、chunk 512、FP8 KV）在同一台机器上扫描每轮提议宽度 K=0/3/4/5/6/7。K 是引擎发给草稿器的候选数，接受长度为其结果；原始记录在 `accept-scan/`。

P3 七道短题（每条约 30 输出 tokens，共 8 次重复宽度运行）：

| K | 接受长度/轮 | 解码 tok/s | P3 正确 | 与普通贪心逐 token 一致 |
|---|---|---|---|---|
| 0（关草稿） | — | 27.7 | 7/7 | — |
| 3 | 2.79 | 13.3 | 7/7 | 7/7 |
| 4 | 3.60 | 46.1 | 7/7 | 7/7 |
| 5 | 4.53 | 23.7–43.0 | 7/7 | 7/7 |
| 6 | 4.69 | 45.7 | 7/7 | 7/7 |
| 7 | 5.19 | 35.8–48.1 | 7/7 | 7/7 |

P3 宽度 7 接受率约 74%（5.19/7），但每轮固定成本（特征传输 + MLX 草稿 + 目标验证）让宽度 3 反而比普通解码慢一倍。K=4–7 为甜点区，相互差距在噪声内。

名录抽取（四条约 300 输出 tokens，宽度 4/7 各跑两遍）：

### 慢尾现象（本次扫描新复现）

同一宽度、同一行的解码时间在不同运行间从约 7 秒跳到 32–153 秒，草稿计数和最终序列完全不变。宽度 4、6、7 都出现过，宽度 5 的运行恰好全程干净。引擎 decode 计时本身就膨胀，说明停滞在目标前向或特征路径，而非 Python 计时误差。候选原因按可能性排序：内存压力（引擎 workSet 10.8 GiB + 生产双槽服务常驻，机器 24 GB，swap 抖动符合非确定性）、IPC/MLX 草稿线程竞争。这是当前解码路径最大的剩余优化点——消除慢尾比继续调宽度收益大，建议下一轮用带时间戳的逐轮日志定位。

### 结论

- 专用单槽 DFlash2 维持宽度 7，共享双槽默认关闭草稿；宽度 5 是同档位的安全替代，遇到验证异常时可降参排查。
- 宽度 3 明确为负收益，不要降到这个区间。
- 进一步提速方向：消除慢尾（第一优先）、压缩特征传输、草稿器侧 MXFP8/编译优化。

### 名录慢尾逐轮采样与单流 200 tok/s 预算

第一批 298 个 token 解码 7.65 秒，与普通贪心逐 token 一致。跳过首轮后，从草稿就绪到下一轮请求的耗时中位数为 139.4 ms，接收特征 0.5 ms，草稿计算到候选就绪 22.8 ms。第二批的首轮草稿就绪后，下一轮请求隔了 45.98 秒。停顿期间，目标进程的一秒采样全部 62 个主线程样本停在 Metal `forward_batch` 等待命令缓冲区完成，草稿进程等待 socket 输入。最接近这段区间的两次系统 VM 采样相隔 45.63 秒，共换入 25.30 GB、换出 23.09 GB。系统换页与停顿同时发生，尚无法将换页归因到具体进程或权重页。首轮草稿本身用时 12.87 秒，下一轮只有一行新特征，草稿阶段也耗时 11.48 秒。捕获停顿后提前结束隔离压测，第二批无完整解码时间。原始数据在 `/tmp/dageno-modelbench/tail-latency/`。

按既有四批名录每轮接受 6.34 个候选、另提交一个目标 token 估算，单流 200 tok/s 要求整轮平均不超过 36.7 ms。即便七候选全中也只有 40 ms。以目标侧 27 ms、草稿与传输 9 ms 为工程预算，优先通过 GPU 命令时间戳拆分排队和执行，定位目标前向中的耗时内核，同时在同一内存预算内测量专家驻留策略。固定 K 的输出一致性检查需继续保留。
